## Context

Команда использует Excel для учёта расходов. Нужно заменить его простой CLI-утилитой на Python. Проект новый, кодовой базы нет. Единственный пользователь — один человек, работающий локально.

## Goals / Non-Goals

**Goals:**
- Минимальный friction при добавлении расхода (одна команда)
- Читаемый список расходов с фильтрацией по датам
- Сводка по категориям для понимания структуры трат
- Нулевая настройка: запустил и работаешь

**Non-Goals:**
- Веб-интерфейс или API
- Многопользовательский доступ
- База данных (достаточно JSON-файла)
- Экспорт в другие форматы
- Мультивалютность

## Decisions

### 1. CLI-фреймворк: argparse (stdlib)

**Выбор:** `argparse` из стандартной библиотеки.

**Альтернатива:** `click` — удобнее для сложных CLI, но добавляет зависимость. Для трёх подкоманд argparse достаточен и не требует `pip install`.

### 2. Хранение: один JSON-файл

**Выбор:** `expenses.json` в текущей рабочей директории.

**Формат:**
```json
[
  {
    "id": "uuid4",
    "amount": 500.0,
    "category": "еда",
    "date": "2026-07-29",
    "note": "бизнес-ланч"
  }
]
```

**Альтернатива:** SQLite — избыточно для одного пользователя и десятков/сотен записей. JSON читается глазами, легко бэкапить.

### 3. Структура проекта: один модуль

**Выбор:** Один файл `expense_tracker.py` с точкой входа через `if __name__ == "__main__"`.

**Альтернатива:** Пакет с разделением на модули (storage, cli, models). Не нужен при таком объёме — вся логика помещается в ~200 строк.

### 4. Категории: фиксированный список

**Выбор:** Перечисление в коде: `еда`, `транспорт`, `жильё`, `развлечения`, `прочее`. Валидация при вводе.

**Обоснование:** Свободный текст приводит к разнобою («обед» vs «ланч» vs «еда»). Фиксированный список — проще для сводки.

### 5. Даты: ISO 8601 (YYYY-MM-DD)

**Выбор:** Строки в формате ISO. Фильтрация — лексикографическое сравнение строк.

**Обоснование:** Не нужен `datetime` для сравнения, формат однозначный, сортируется естественно.

## Risks / Trade-offs

- **JSON-файл растёт** → Для сотен записей не проблема. Если станет тысячами — можно мигрировать на SQLite позже.
- **Нет блокировки файла** → Один пользователь, конкурентный доступ не ожидается.
- **Потеря данных при сбое записи** → Запись через временный файл + rename (атомарная операция на POSIX).
- **Категории захардкожены** → Изменение требует правки кода. Приемлемо для внутреннего инструмента.
